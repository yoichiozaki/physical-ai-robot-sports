## E3 残差学習（`scripts/residual.py collect/train` → `checkpoints/residual/`, `results/residual/train.json`）

- 1 回目: ランダム化条件（毎球条件が変わる）で 6,000 球を収集 → 検証誤差 0.41 → 0.39 m とほぼ改善なし。
  誤差の大部分が「その球の物理パラメータ」で決まり、特徴量から予測できないため。
- 2 回目: 標準条件（ホームコート）で 2 回収集した 5,718 球（学習 4,575 / 検証 1,143）→ 検証誤差の中央値
  19.9 → 9.3 cm（平均 25.3 → 16.1 cm）。学習 2.8 秒（CPU）。
- → 残差学習は「同じ環境での反復練習」で効く。環境が変わると補正は外れる（E4 の表で未知条件では悪化・効果なし）。

開発の経緯（未知条件のドリル結果を見ながら設計した。試合評価のシードは使っていない）:
1. 着地誤差の EMA（OnlineBias）: 未知: 強風 0.463 → 0.434 m と小さな改善のみ、未知: コートは改善せず。
2. 打撃ゲインの適応（ImpactAdapter, EMA 0.5）: 効果なし。標準条件では残差補正と干渉して悪化（0.100 → 0.133 m）。
   未知: コートで打ち返せる球が少ないのは「打ち方」ではなく「来る球の予測（バウンド）」が外れるためと判明。
3. → **オンライン系同定（ModelAdapter）**: バウンド前後の速度から e・μ、飛行中の水平減速度から抗力・風（RLS）。
   未知: コートで打ち返せる球が 72 → 456 球。ただし標準条件で残差と併用すると 0.100 → 0.314 m に悪化

4. → **変化検知**: 推定値が標準モデルから有意に離れたとき（|Δe| > 0.06, |Δμ| > 0.12, 抗力 ±30%, 風 > 0.8 m/s,
   打撃ゲイン ±6%、最低観測数あり）だけ同定値を使い、そのとき残差を停止。上表の最終列。

同定値の妥当性（試合終了時、B*、`results/eval_main/matches.csv`）: 未知: 強風で k_d = 0.0311（真値 0.030–0.034）、
風 2.15 m/s（真値 2.0–2.5 m/s）。未知: コートで e = 0.875（標準 0.735）、μ = 0.078（標準 0.284）、打撃ゲイン 1.029。

## E5 強化学習（`python -m tennis.learning.train --config configs/training/ppo_{hybrid,direct}.yaml`）

- 環境: 1 判断 = 自分のショット 1 回。1 エピソード = 4 ポイント、報酬 ±1 + イン 0.1。相手 5 種 × 標準/ランダム化。
- スループット: 1 判断 ≈ 1.5–2 秒のシミュレーション ≈ 0.2–0.4 CPU 秒。SB3 の SubprocVecEnv は全環境の同期待ちのため、
  判断ごとの所要時間のばらつきが大きいこの環境では CPU 利用率が約 1/3 に落ちた。2 ランを並列に 16 環境ずつ走らせて補った。
- 予測器の内側ループを最適化（加速度計算のインライン化、ビット単位で同一の結果をテストで保証）して 1.6 倍高速化。
- 予算: 当初 12 万判断/ラン → 実測 9–20 判断/秒のため D 64,000、C 48,000 判断に縮小（DECISIONS T-015）。

## E6 破棄した初回の評価・学習（規則の不具合の発見）

最初のベースライン評価（960 試合）と学習は、2 つの不具合を含んでいたため破棄した（数値は成果物に使っていない）。

1. **ポイント間の間がない**（T-018）: 動画用にラリーを探したところ、D 対 安定型の全ポイントが 1 打で終わっていた。
   D のサーブはエース、相手のサーブは「serve not hit」（前のポイントで振られた相手ロボットがトスに間に合わない）。
   ルール戦術 B+（オープンコート狙い）も同じ現象で得をしていた（初回評価では B+ 90% > B 71%）。
2. **サーブが長い**（T-019）: 全プレイヤーのサーブが 0.8–0.9 m 長く、相手のサーブの多くがフォルト。

教訓: 強化学習と手作り戦術の両方が、シミュレーションの規則の穴を「最適解」として使ってしまう。数値が良すぎる・
ラリーが極端に短いといった兆候を、実際の試合の映像・ログで確認することが不可欠だった。

## E8 発展1: 自己対戦リーグ（`configs/training/ppo_league.yaml` → `checkpoints/ppo_league/`, `results/league/`）

- 学習: D から開始、96,768 判断（ローカル CPU 4.0 時間、5 判断/秒）、1.2 万判断ごとに世代を追加（世代 0–8）。
- 評価: 総当たり戦（世代 0–8、B/B+/B*、スクリプト 5 種 = 17 者、各組 4 試合 × 12 ポイント = 544 試合・6,528 ポイント、
  `python scripts/league_eval.py`）。Bradley–Terry（Elo 尺度、世代 0 = 1500、サーブ有利を推定）、試合単位ブートストラップ。

| 選手 | Elo [95% CI] |
|---|---|
| 世代 0（= D）〜 世代 8 | 1484–1507（全世代の区間が重なる。世代 8 = 1507 [1488, 1526]） |
| スクリプト「攻撃型」 | 1229 |
| B* / B+ / B | 1014 / 943 / 911 |
| スクリプト ランダム / 安定型 / 低速 / ロブ | 860 / 741 / 690 / 600 |

**自己対戦では強くならなかった。** 原因は 1 本のサーブ:
- 学習済み方策（D を含む全世代）がサーブすると 99.7–100% がエース（受け手が誰でも）。それ以外の選手のサーブのエースは 5–10%。
  同じ強さならサーバーがポイントの 80% を取る（サーブ有利のロジット 1.36）。学習済み同士の対戦は全ポイントが 1 打で終わる。
- そのサーブは「深く・左（受け手のフォア側）・7 m/s」（rl-222）。世代 0（D）は 3 種の狙いを約 3 割ずつ使っていたが、
  世代 1 以降は 97–100% がこれ。
- 原因の特定（`python scripts/diagnostics/serve_trace.py`）: このサーブは受け手のベースラインぎりぎりに弾み、低いまま受け手ロボットの台座の横を
  抜ける。レールは取り付け位置より後ろへ下がれず、腕は台座に近すぎる球を打てないので、受け手は打点候補を 1 つも見つけられない
  （「chase」のまま）。人間のテニスなら後ろへ下がって打つ球で、ロボットの設計上の死角。
- ラリー中の球（サーブ以外）は、学習済みの受け手なら全ゾーンで 87–100% 返球できる（`league_returns.png`）。死角はサーブだけ。
- D のもとの評価への影響: 総当たり戦で D は、自分のサーブではほぼ全勝、相手のサーブでも B/B+/B* と 4 種の相手には 96–100%、
  攻撃型には 46% のポイントを取った。D の優位はエースだけによるものではないが、数値はエースで底上げされている。
- 攻略役（exploiter）: D だけを倒すように D から 2.46 万判断学習させた方策と D の対戦は 480 ポイントでちょうど 50%
  （両者とも自分のサーブを全部取る）。サーブで勝負が決まるゲームでは、方策の強弱を測れない。

教訓: 自己対戦は、ルールとロボットの設計の穴を最初に見つける（ポイント間の間 T-018 に続いて 2 例目）。実際のテニスの
「サービスボックス」ルール（サーブはネットから 1.62 m 以内に入れる、実コートと同じ比率）を加えると、D 同士の 1 ポイント
あたりの打球数は 1.0 → 6.0 になった。このルールで D を微調整し、自己対戦をやり直した（E9）。

## E9 発展1 続き: サービスボックスありの自己対戦（`ppo_hybrid_sb.yaml` → `ppo_league_sb.yaml` → `results/league_sb/`）

ルール: サーブの最初のバウンドはネットから 1.62 m 以内（`GameConfig.service_line`、実コートと同じ比率）。全選手の
実行層がこのルールを知っていて、サーブの狙いは手前 1.27 m 以内・球速 5 m/s 以下に制限される。

1. D を新ルールで微調整（3.28 万判断、31 分、スクリプト相手 5 種）→ 評価エピソード 16 回すべてに勝利。これを世代 0 とする。
2. 自己対戦リーグ（7.2 万判断、1.5 時間、13 判断/秒）→ 世代 0–6。
3. 総当たり戦（世代 0–6、B/B+/B*、スクリプト 5 種 = 15 者、420 試合・5,040 ポイント）。

| 選手 | Elo [95% CI] |
|---|---|
| 世代 2・3・5・6 | 1709–1715（区間 ≈ 1650–1778） |
| 世代 4 / 世代 1 | 1693 / 1679 |
| スクリプト「攻撃型」 / **世代 0** | 1507 / **1500** |
| B / B* / B+ | 1416 / 1411 / 1336 |
| スクリプト ランダム / 安定型 / 低速 / ロブ | 1232 / 1142 / 1095 / 938 |

- ゲームが成立した: 学習済み同士のラリーは 1 ポイント平均 3.2 打（ルール変更前は 1.0 打）、エースは 0.8%（同 100%）。
  サーブ側の有利は逆転し、同じ強さなら**レシーブ側**がポイントの 71% を取る（サーブ有利のロジット −0.91）。
  短いサーブはレシーバーに最初の攻撃の機会を与えるため。
- **Elo は 2.4 万判断で約 +210 上がり、その後は横ばい。** ただし内訳を見ると、上昇のほとんどは出発点（世代 0）への圧勝
  （世代 3・6 は世代 0 から 98% のポイント）によるもので、固定の相手に対しては世代 0 とほぼ同じ
  （対 B 0.58 → 0.56–0.67、対 B* 0.92 → 0.81–0.94、対 攻撃型 0.71 → 0.65–0.73）。世代 1–6 どうしはほぼ互角（0.46–0.54）。
- 戦術は「深く・速く」に収束（世代 6: 深い左 91%・深い右 9%。世代 0 は中間の深さを 65% 使っていた）。世代 6 対 世代 0 の
  48 ポイントの内訳は、世代 0 が返せなかった 34、世代 0 のネットミス 13。難しい打点から中間の深さを狙うと
  ネットにかかりやすく、深い球（高い弾道）の方が確実、という戦術を学んだと解釈できる。
- 結論: 公平なルールなら自己対戦は短時間で「出発点を打ち負かす」戦術を見つけるが、得られる強さは「自分の系統に対して」の
  ものが中心で、ベンチマーク全体への汎化は限られた。汎用的な強さには、より多様な対戦相手（攻略役、人間のプレーデータ）や、
  より細かい行動空間（狙いの連続化・回転）が必要。

| VLA 単独・遅れ 0（考える時間ゼロ） | 4% / 0% | 5% / 0% | 7% / 0% |
| VLA 単独・遅れ 0.1 / 0.2 / 0.36（実測）/ 0.4 秒 | 0–1% / 0% | 1–6% / 0% | 2–4% / 0% |
| 階層型（VLA が狙い、物理が打つ）・遅れ 0.36 秒（実測） | 98% / 89% | 98% / 93% | 100% / 100% |

- **VLA 単独は、どの惑星でも、考える時間がゼロでもほとんど当たらない。** 外したときのラケットとボールの最接近距離の中央値は
  0.57–0.67 m（エキスパートの打球時は 0.05–0.09 m）で、惜しいのではなく、まったく違う場所・時刻に振っている。試合の速さ
  （2.5 倍遅い月）でも改善しないので、ボトルネックは遅れではなく精度（何の精度かは E10b で切り分けた）。
- 開発中の診断（5,000 ステップ時点、月、30 タスク）: 1 回ごとに新しいノイズで行動を生成する代わりにエピソード内でノイズを固定
  しても（7%）、0.5 秒ずつまとめて実行しても（0–3%）改善せず、行動チャンクの一貫性の問題でもない。2 万ステップまで学習しても
  （損失 0.043 → 0.018）命中は改善しなかった。
- **階層型は教師と同等。** 相手を見ないと従えない指示（“away from / straight at the opponent”）でも 87%（地球）・94%（火星）・
  100%（月）。画像と言葉から「どこへ打つか」を決める能力は十分にある。
- **階層型の「考える時間」の上限**（指示どおりの割合が半分になる遅れ、`hier_sweep*`、各 60 タスク）: 地球 1.14 秒・火星 1.75 秒・
  月 3.08 秒。地球換算（遅れ × 世界の速さ s）にすると 1.14・1.08・1.25 秒でほぼ一致し、限界は世界の速さで決まる
  （`vla_hier_latency.png` の右図で曲線が重なる）。それを超えると答えが打点の確定に間に合わず、既定の狙い（深い中央）に打つ。

### E10b 対照実験: ボールの位置と速度を直接入力（T-027 → `results/vla/ball/`, `results/vla/ball_period/`）

同じデモの関節状態にボールの位置と速度（真値、6 次元）を加えて学習し直し（`make_dataset.py --ball-state`、2 万ステップ、
損失 1.64 → 0.012、A100 で 3 時間 46 分）、本番と同じ 100 タスクで評価した（`scripts/vla/colab/eval_ball.sh`、18 条件を 1 台の
A100 で並列実行）。値は 命中 / コートに入った / 指示どおり。

| 遅れ | 新しいチャンクに切り替える周期 | 地球 | 火星 | 月 |
|---|---|---|---|---|
| 0 | 0.1 秒 | 49 / 15 / 4% | 47 / 5 / 3% | 37 / 8 / 2% |
| 0.1 秒 | 0.1 秒 | 40 / 9 / 2% | 7 / 1 / 0% | 10 / 1 / 1% |

| 0（診断） | 0.2 秒 | 69 / 26 / 5% | 53 / 12 / 3% | 38 / 5 / 2% |
| 0（診断） | 0.36 秒 | 69 / 24 / 8% | 52 / 11 / 2% | 53 / 4 / 2% |

- **画像からボールを捉えることが最初のボトルネック。** 命中は画像のみ（どの条件でも 0–7%）から、遅れ 0 で 37–49%、最良の条件で
  69% に上がる。外したときの最接近距離の中央値も 0.57–0.67 m → 0.23–0.28 m（崩れた 2 条件を除く）に縮み、ラケットが最も
  近づく時刻はエキスパートの打球時刻から中央値で ±0.15 秒以内。振るタイミングはおおむね合っている。
- **次のボトルネックは打球の精度。** 当たった球のうちコートに入るのは 21%、そのうち指示どおりのゾーンは 28%（174 球、95% CI
  22–35%。1 ゾーンの面積はコートの約 1/6）。同じネットワークの「狙い」の出力は階層型で 89–100% 正しいので、どこへ打つかは
  分かっていても、関節の動きでそれを実現できない。
- **遅れの影響は単調ではなく、行動チャンクのつなぎ方が効く。** 同じ切り替え周期（0.2・0.36 秒）で遅れ 0 と比べた遅れそのものの
  影響は 10 ポイント以内。一方、0.1 秒ごとに 0.1 秒古い答えへ切り替えると火星 7%・月 10% に崩れ、遅れ 0 でも 0.1 秒ごとの
  切り替えは 0.2–0.36 秒ごとより悪い（地球 49% → 69%）。遅い世界ほど楽になるわけでもない（遅れ 0 で月 37% < 地球 49%）。
  end-to-end の VLA では、遅れの長さよりも、短い間隔で古い予測へ切り替え続けることが害になる。行動チャンクをなめらかに
  つなぐ工夫（temporal ensembling、real-time chunking）が要る理由がここにある（`vla_ball.png`）。
